# Playful P4 lesson experience — proposed decimal slice

**Implementation update (2026-10-06):** The user waived Claude review for this phase. Codex implemented the integrated scope; see [plan outcome](playful-p4-practice-plan.md) and ADR 008. The proposal below records the planning rationale, not an outstanding review gate.

**Status:** Documentation-only proposal for the next single Claude review and Codex disposition. No application changes or publication approval.  
**Date:** 2026-10-06.  
**Owner:** Codex lesson-experience planning agent; ownership recorded in `handover.md` before writing.

## User goals and proposed scope

The user wants lessons to carry the playful, modern character of the home page, rather than returning to a generic worksheet layout. The user also wants new examples with different variables to reinforce and check application of a method. The accepted palette and current Outfit/Atkinson fonts remain. P4 remains the priority; further P2/P3 expansion remains paused.

The following details are proposed engineering and design choices, not claims about generational preferences or established learning efficacy. Build one complete experience around the existing `p4-decimal-add-subtract` lesson, initially its subtraction-with-regrouping objective. Include initial action, incorrect and malformed responses, all four hint rungs, correct step, reflection, completion, replay and deterministic “Try another.” Reuse the existing assessed lesson sequence. Do not extend every topic or add a new reward/progress system in this slice.

## Observed starting point

Inspected `src/ui/lesson-view.ts`, `src/topics/decimals.ts`, `src/ui/visuals.ts`, relevant styles, the saved decimal lesson and the existing screenshot `docs/screenshots/topics/p4-decimal-add-subtract.png`. This is source/screenshot inspection, not a fresh browser audit.

The shared canvas already presents one assessed step at a time and preserves assessment through the common runtime. The issue is presentation: a large header, full step rail and static mathematical table precede the active prompt on a phone. In the saved 390px-wide screenshot, the active prompt begins roughly 950px down the full-page capture. All topic families use similar bordered visual/question cards. The visual is generated from the lesson, without active-step or hint disclosure context. Hints and completion remain detached from that visual. The current decimal table has a 420px minimum width and needs sideways scrolling.

The proposed improvement is to make the mathematical representation the activity, while retaining a clear answer action and the existing deterministic assessment. A smaller header alone would improve access but would not make the activity feel different.

## Concrete visual direction

Use a single cream workbench with the existing decimal green accents, rounded numeral tiles, fine place-column guides and a restrained star/flower motif from the home. Most of the surface contains useful mathematics. Avoid a decorative story setting, large mascot, timers, points, streak pressure, sound or confetti. Topic identity comes from how the mathematical objects look and respond.

### Desktop, nominal 1280 × 800

Use a centred shell no wider than 1120px. A compact top row contains Back to decimals, the topic icon/name and the two learning modes. A small title row follows; show the objective in one sentence rather than a large repeated introductory block. Keep the draft-preview notice visible where applicable.

Below it, use a two-column activity surface: roughly 60% mathematical workbench and 40% active action, with a 24px gap. The left begins with the actual problem in large tabular numerals: `7.25 − 2.6 = ?`. The right begins with “1 of 3 · Line up the places,” then the active prompt, controls and check button. The active prompt and check control must be in the initial 1280 × 800 viewport for the short fixture; long/custom content can grow naturally.

The workbench displays ones, tenths and hundredths, rather than a large four-place reference table irrelevant to this task. The subtraction operator sits outside the digit columns. A matching-column illustration sits within the same surface, with decimal points clearly anchored. Full place-chart reference and representation description remain available in a labelled “Place-value reference” disclosure below, rather than dominating the screen.

The progress indicator uses three compact labelled markers: Line up, Calculate, Explain. Completed markers have a check and text; the active marker has `aria-current="step"`. Learner markers do not permit skipping required goals. There is no separate celebratory page between steps.

### Phones, 320–412px wide

Use one column in semantic order: compact navigation/mode controls; concise title and progress; actual expression; active prompt and response controls; feedback; hint disclosure; optional reference and facilitator tools. Merge the visual and response areas into one activity surface rather than stacking two padded cards.

The task expression remains at the top of the surface on each step. It can scroll off-screen: do not force a sticky header that covers controls, the software keyboard or enlarged text. No page-level horizontal scroll. The compact three-place workbench fits at 320px without sideways scrolling or shrinking numeral text below 18px. At native 200% zoom, reflow into a taller surface if necessary; never crop place columns. The reference chart may retain an explicitly labelled scroll region if necessary, but completing the active task must not require it.

At 390 × 844 with the standard draft notice and collapsed hints/reference, the expression, active prompt and the first actionable choice/input must be visible initially. The check button may be below the fold when all three readable explanation choices are present; do not compress text or touch targets to force everything into one screen. The app header, lesson title and progress before the workbench should occupy at most roughly 220px for this short fixture. These are acceptance targets to verify in-browser, not guarantees from this document.

Alignment options remain radio choices in this slice. Their diagrams make them tangible without inventing a drag-and-drop requirement or adding an unassessed interaction that masquerades as conceptual assessment. A future direct-placement task could replace the choice goal, with its own authored action contract and fixtures; it is explicitly outside this slice.

## Guidance, editing and representation disclosure

“Learn together” uses the same workbench, inputs and validators. Facilitator prompts appear in a labelled collapsible area separate from the learner action. No timed progression. Entering guided mode marks facilitator support and changing back preserves it. Reveal/replay/reset follow the same explicit rules as independent mode.

`mountLessonView` remains the shared learner/author presentation. Keep the editable `data-region` anchors for title, objective, story, visual, active prompt, choices and hint. Author navigation still visits any step without assessing it; hint inspection shows that rung's permitted visual state. Freeze the whole authored lesson during an author trial. Author edits, undo/redo and switching back to edit must not rewrite that frozen trial. Region overlays must not cover the radio buttons or input.

The author sees initial and hint treatments through existing edit navigation/hint inspection; success treatments are reached by completing the frozen trial normally. This phase adds no arbitrary success-state preview controls. Generated variants and “Try another” are absent from author trials, and generated-example draft saving is deferred to a later phase. No raw JSON editing is required for this user flow.

## Proposed implementation boundaries

1. **Shared activity shell:** `src/ui/lesson-view.ts` and scoped styles own compact navigation, workbench/action composition, feedback placement, progress, completion and focus. They must not import concrete decimal logic or generation samplers. Retain the ordinary presentation as a fallback for all other lessons.
2. **Optional topic presentation capability:** register a topic-owned activity renderer/controller through application composition. Its view context includes active step, author/trial presentation, hint rung and correctly assessed goals, not a learner-controlled success flag. The exact TypeScript shape is an implementation-plan decision. Keep it separate from adapter mathematical authority and make absence fall back cleanly.
3. **Decimal presentation:** a decimal-specific module derives the compact columns and permitted exchange overlay from integer coefficients/scales. It does not change the parser or grade submitted answers. Only the explicitly identified authored decimal slice selects the richer presentation; custom edits, addition or unsupported hint wording must fall back unless independently supported. Do not automatically enable a mathematically valid exchange overlay under arbitrary author text.
4. **Generation/continuation:** a separate variant service owns constraints, seed, template/version identity, coherent package construction, validation, duplicate handling and publication policy. The UI invokes it through a supplied continuation callback, never through topic imports in the shared runtime. If no eligible generator is registered or generation fails, retain the completed attempt and existing replay/back controls, with an actionable message. Never reset first and generate afterwards.
5. **State:** mount/unmount and delayed visual effects cannot update a newer attempt with an older result. Fresh variant assessment state is isolated; mode choice may carry forward, while new support flags derive from that mode and later actions. Finishing through facilitator mode cannot count as unsupported practice. No new persistence, analytics, account or third-party calls.

The phase requires a content-impact assessment even if JSON bytes stay unchanged: new diagrams, equivalent decimal displays and disclosure overlays can affect mathematical/teaching meaning. Existing exact-payload approval rules remain until a separately assessed generator release policy exists. A valid deterministic variant is still unapproved in development preview; this UX proposal does not grant template-wide learner publication approval.

## Acceptance and verification proposed for implementation

- Complete this one decimal fixture from start through reflection using both independent and guided modes, without hints and with all hint rungs; compare assessment/support histories with the existing runtime behaviour.
- Incorrect selection, invalid exact input, wrong exact answer, equivalent correct decimal formatting and repeated checks preserve the correct attempt state. Success/reveal is the only route to showing the final answer.
- Verify initial, incorrect, hint 3, worked reveal, correct and completion screenshots at 1280 × 800 and 390 × 844. Inspect 320, 360, 412 and 768px reflow, long edited prompts/choices, native 200% zoom and the software-keyboard interaction where available; record real-device gaps plainly.
- Complete the whole flow by keyboard and tap without drag. Preserve visible focus; checked/active/error states use text/icons as well as colour. Dynamic feedback uses a concise polite status announcement. Step changes/new variants focus the prompt; invalid submissions focus the input. Hint reveal focuses the help content without losing the return path.
- Screen-reader description exposes given values and the current disclosed representation, not hidden derived answers. Decorative motifs are hidden from assistive technology. Controls have useful labels independent of place-position graphics.
- Reduced-motion disables all movement while leaving correct feedback and all actions available. No infinite lesson-surface motion, sound or animation wait before proceeding.
- Author editing, undo/redo, hint inspection, frozen trials and return-to-edit work in the new surface; outside this slice, existing topics retain working presentations and controls.
- Try another updates variables, prompt, answer, hints and visual atomically; preserves skill and avoids the immediately preceding values; starts an isolated attempt and leaves completed evidence intact. Replays keep the same variant. Generation failure leaves the completed example usable.
- Run targeted runtime/DOM/decimal representation tests, existing suites and browser/release checks appropriate to the integration. Engineering checks do not replace qualified human review of wording, representation, hints or P4 suitability.

## Risks and deferred ideas

The exchange overlay is meaningful but can become over-scaffolding or reveal too much. Keep it behind the explicitly authored hint disclosure; begin new variants with the ordinary action and all hints available. Automatic support fading and difficulty changes are deferred: the earlier proposed “less guidance after a correct answer” is not a new approved rule, and the existing SOW's testable fading baseline cannot be replaced casually.

A single attractive decimal screen must not become a new rigid shell for geometry, fractions or data. Verify the optional presentation boundary and fallback in this phase. Later topic-specific proposals may use partitioning, direct selection or number-line placement when justified; do not repurpose decimal columns for unrelated maths.

No newly asserted misconception feedback, rewards economy, long-term mastery score, avatar system, arbitrary story generation, full catalogue redesign or renewed LLM annotation work. The immediate decision is whether the concrete decimal slice is a good next experience to implement after the single engineering review and Codex assessment.
