# Review of the interactive manipulatives (workbench) plan

**Status: written 2026-10-10 by an independent reviewer agent (Claude) that did not write the plan.** This is a review, not a decision. Codex still has to record accept, modify, reject or defer for each finding. It approves no lesson content or curriculum placement; no human has reviewed anything. Reviewed: `docs/interactive-manipulatives-plan.md` and `docs/interactive-manipulatives-evidence.md`, checked against `src/core/types.ts`, `src/core/runtime.ts`, `src/ui/lesson-view.ts`, `src/topics/{capability,p4-kit,nets,symmetry,angle-measure}.ts`, `src/content/package-validation.ts`, `scripts/check-learner-artifact.mjs`, `content/library.json`, the tests and the built `dist-learner`. No application code, tests, lesson JSON or config were changed. Scratch scripts (hexomino enumeration, a painter's-order probe) live in the session scratchpad outside the repo; their results are quoted below and are my own, coarse, and should be re-done properly in the spike.

## Verdict

**PROCEED WITH THE CHANGES BELOW.** The central claim holds: no new step kind, schema or contract bump is needed, because every first-wave result is a choice, a set or an exact integer, and `src/core/` really can stay untouched. The architecture is sound in outline. But four things must be fixed before WP0b/WP1: the spike would not catch the painter's-order failure I found, two of the six lessons do not actually assess what they claim (the draw step is answered by the number in its own prompt; the `scale` step can reject a valid alignment), the lesson-view lifecycle is understated, and the symmetry grid arithmetic is wrong. None of this justifies stopping.

## Confirmed claims (verified true)

- `Step.kind` is `choice | number | multi | exact` (`core/types.ts`); `Adapter`, `Session`, `Action` and `AssessmentEvent` need no change; `submit` takes only an `answer` action. A workbench that sets the existing controls and submits through the form is honest and needs no schema or contract bump. Packages are schema 1 to 3 (`package-validation.ts`); no `kind` check on tasks, only on topic validators, which would gain new `task` values.
- `lesson-view.ts` rebuilds the visual by `innerHTML` when the string changes (`visualSignature`) and already imports `topicLabel` from the registry. The plan's statement that `src/core/` stays free of concrete topics is true.
- The registry type `RuntimeTopic` is a plain interface in `capability.ts`; an optional `workbench?` member is additive and old callers are unaffected.
- Learner JS about 193 KB, CSS about 43 KB (measured above). Learner sentinels are in `scripts/check-learner-artifact.mjs` and fail the build on a hit; the existing "Shaded squares as row,column pairs" label is already there.
- 35 free hexominoes, 11 cube nets, 24 non-cube hexominoes (my enumeration), and 64 fixed orientations are correct counts for the totals the plan uses.
- The doubled-coordinate reflections (`v:c`, `h:c`, `d1:c`, `d2:c`) are correct; I checked `d2` on its fixed points. With the protractor model, the clockwise second-arm case reads `|turn|` on the inner scale at `rot = a1 - 180`, and the wrong scale reads `180 - |turn|`.
- MDN's list of properties forcing `transform-style: flat` matches the plan (see R-110 for the nuance). WCAG 2.5.7 (AA, keyboard alone is not enough), 2.5.8 (24 px), 2.5.5 (44 px, AAA) and 2.3.3 (AAA) are as characterised, from my own knowledge.
- No existing test hard-codes a library count of 57 or 672 lessons; `tests/home-layout.test.ts` derives its counts from the topics present, so adding lessons to existing topics does not break it. `tests/spotlight.test.ts` uses synthetic topics.
- Existing starters stay byte-identical if only new files and new task values are added; `tests/p4-kit-regression.test.ts` already guards the symmetry family.
- The previous plans' pattern for adding task values without a bump is consistent with ADR-009.

## Unverifiable items (not confirmed by me)

- Whether `touch-action` is honoured on SVG child elements in Safari and Chromium, and iOS Safari pointer behaviour: needs a device or at least WebKit.
- jsdom 30's `PointerEvent` support (the plan marks it as own knowledge).
- The content width available for the shade grid at 320 and 360 px: needs a browser measure.
- All evidence items E1 to E9, S1 to S5 (web summaries, not primary pages), including Polypad, PhET, MLC and CPA claims; the MOE syllabus placement; the sizes of any real learner error rates.
- My painter's-order probe is coarse (centroid sort, 18 by 18 samples, reduced state set, four-quadrant views). It shows the failure exists; it does not give a rate.
- Frame cost and low-end phone behaviour; screen-reader behaviour of the live regions.
- The 14-net pool depends on the rolling-cube model matching `foldsToCube` on those nets (I re-implemented the roll; the repo's own function was not run).
